# Detail-level experiments: plan, commands, and reasoning

This document plans experiments and visualisations in Unreal that revolve
around one question: **how much detail should the voxel city carry, where,
and at what cost?** Detail is not one knob but a chain of dials, from
voxelisation to the viewer. Each dial is explained below (what it changes,
what it costs, why you would turn it), followed by concrete experiments
with commands and measurement recipes. Companions: [PIPELINE.md](PIPELINE.md)
for the base chain, [VISUALISATIONS_AND_EXPERIMENTS.md](VISUALISATIONS_AND_EXPERIMENTS.md)
for the broader idea list, `../AssistingRuns/docs/` for format internals.

## Part 1 - The detail dials

| # | Dial | Where it is set | Cost to change |
|---|---|---|---|
| D1 | Voxel resolution (`--cell-xy`, `--cell-z`) | voxelisation (`area_cli`) | highest: re-voxelise (tens of minutes to hours) |
| D2 | Grouping (`--group-intervals` / `--no-group-intervals`) | voxelisation | same run produces both stores |
| D3 | Leaf tile size (`--tile-m`) | export (`tileset_cli from-store`) | minutes: re-export from the store, not from a payload |
| D4 | Pyramid vs flat (`--flat`) | export | minutes; flat is only safe on small regions |
| D5 | Class subset (`--keep-classes`) | export (`from-store`) | minutes |
| D6 | Spatial subset (`--region`) | export (`from-store`) | minutes |
| D7 | Screen-space error (MSSE) | viewer (Unreal/Cesium actor) | free, live |
| D8 | Physics meshes on/off | viewer (tileset actor) | free, but expensive when on |

**D1, voxel resolution.** The source store fixes the finest detail that can
ever reach the screen. You do not need to re-voxelise for these
experiments: the resolution sweep already covers the same 3 x 3 km area
at four resolutions, each with payloads ready for export, at
`TestOutputs/RunN/area_output/area_stream.{bin,idx.json}` relative to the
Python project root. That sweep is a local run tree - it is regenerated by
re-running `area_cli` with the parameters in the table, and is not part of
the delivered files, so the commands below assume you have produced it or
will substitute your own run directory.

| Store | cells (xy/z) | records (payload) | note |
|---|---|---|---|
| TestOutputs/Run1 | 1.0 / 1.0 | 18.0 M | grouped |
| TestOutputs/Run3 | 0.5 / 0.5 | 58.0 M | grouped |
| TestOutputs/Run5 | 0.25 / 0.25 | 187.2 M | grouped |
| TestOutputs/Run7 | 0.25 / 0.1 | 187.3 M | grouped |
| TestOutputs/Run8 | 0.25 / 0.1 | 317.4 M | raw (no grouping) |

Why it matters: resolution drives every downstream cost (records, GLB
bytes, GPU instances) roughly linearly, and the visual payoff saturates:
somewhere between 1.0 m and 0.25 m the city stops looking "more real" at a
given viewing distance. Finding that saturation point per use case is E1.

**D2, grouping.** Grouping merges consecutive same-class runs in each
column before outputs are drawn. It removes 13 to 41 percent of records
(more at finer z) but bridges vertical gaps, so a tree crown floating
above trunk space becomes one solid run. Raw preserves the gaps. The
visual difference lives at facades and canopies; the cost difference is
the record count. E2 measures both.

**D3, leaf tile size.** The exporter cuts the area into square leaf tiles
(default 100 m). Smaller leaves mean finer streaming granularity (the
viewer fetches only what it looks at) but more files and more requests;
larger leaves mean fewer, heavier fetches. E4 finds the sweet spot.

**D4, pyramid vs flat.** The level-of-detail pyramid is what makes
whole-area viewing possible at all: without it every leaf loads at once
(4.2 GB, 187 M instances, engine limits, crashes; see
`../AssistingRuns/docs/03_troubleshooting.md`). `--flat` exists for tiny
subsets and as the control condition in E5. Never use it on a full area.

**D5, class subset.** Detail budget is not only geometric: a
vegetation-only tileset (`--keep-classes 3,4,5,8`, matching
`VEGETATION_CLASSES`) at fine resolution can be combined with a coarse
everything-else tileset. Thematic detail where the analysis needs it,
cheap context everywhere else. E6 builds that composite.

**D6, spatial subset.** `--region xmin ymin xmax ymax` exports one
neighbourhood at full detail: small, fast, fits free hosting tiers, safe
for flat mode and physics. The close-range inspection tool. E7 uses it.

**D7, screen-space error.** The one free dial. The viewer refines a tile
when its declared geometric error projects to more than MSSE pixels. The
recorded sweep in
[../AssistingRuns/docs/01_pipeline_overview.md](../AssistingRuns/docs/01_pipeline_overview.md)
puts the useful band at 4 to 16: 4 is desktop-inspection sharpness, 16 is
the Cesium/Unreal default and is sane for this content, while 32 and 64
render identically to 16 at whole-area range and only lose shape up close
(roof form is already gone at 32). At 128 the city becomes an abstract
coarse model instantly, with no re-export. E3 re-runs the sweep in Unreal.

**D8, physics.** Collision cooking for hundreds of thousands of boxes per
tile was the single largest memory consumer in early tests (34 GiB
crash). Keep *Create Physics Meshes* off except on small regions where
line traces are actually needed (sight-line studies).

## Part 2 - Experiments

Every experiment follows the same recipe: export (if needed), serve each
tileset on its own port, add one `Cesium3DTileset` actor per tileset in
the `IarbreVoxels` level, and capture the fixed viewpoints with
`tools/example_screenshot.py` so results are comparable across runs.

Run every command below from the Python project root - the directory that
holds the `voxelizer` package, so `python -m voxelizer.*` resolves. Store
and payload paths are relative to it, and each `--out-dir` lands there.

### E1 - Resolution ladder: where does visual payoff saturate?

Export the four grouped sweep stores (payload path, fastest):

```powershell
for %R in (1 3 5 7) do python -m voxelizer.tileset_cli from-payload ^
    TestOutputs\Run%R\area_output\area_stream.idx.json ^
    TestOutputs\Run%R\area_output\area_stream.bin ^
    --out-dir Run_res_%R --crs EPSG:3946
```

Serve on ports 8765 to 8768, add four actors, keep one visible at a time.
Capture the same three viewpoints per tileset: whole area, district
(~500 m), street (~50 m). Measure per resolution: tileset disk size, GPU
geometry MB at each viewpoint (Cesium stats), frame time (`stat unit`).
Why: this answers, with pictures and numbers, which resolution each
IA.rbre use case needs: massing and communication (1.0 m), district
analysis (0.5 m), street and canopy work (0.25 m). Expected: the street
view is the only one that visibly rewards 0.25 m; the whole-area view
looks identical from 1.0 m upward because MSSE serves coarse levels
anyway.

### E2 - Grouped vs raw: what does grouping cost visually?

```powershell
python -m voxelizer.tileset_cli from-payload TestOutputs\Run7\area_output\area_stream.idx.json TestOutputs\Run7\area_output\area_stream.bin --out-dir Run_grouped --crs EPSG:3946
python -m voxelizer.tileset_cli from-payload TestOutputs\Run8\area_output\area_stream.idx.json TestOutputs\Run8\area_output\area_stream.bin --out-dir Run_raw --crs EPSG:3946
```

Same resolution (0.25/0.1), 187 M vs 317 M records. Compare: disk and
load cost (expect ~1.7x), and close-up captures of a facade and a tall
tree. Why: grouping merges across vertical gaps, so raw is the honest
record of what the LiDAR saw (gaps included) while grouped is the solid,
cheaper rendering. The experiment documents what is actually lost:
expect visible differences only where real gaps exist (under canopies,
balconies, wire structures), and none in plan view. This puts numbers
and pictures behind the default-grouped choice.

### E3 - MSSE sweep: free detail control at runtime

One tileset (Run_res_5), one viewpoint per capture, sweep *Maximum Screen
Space Error* = 8, 16, 32, 48, 96, 128. Record frame time, GPU geometry
MB, and tiles selected at each step (all visible live; no re-export).
Why: the engine-side dial should be exhausted before anyone re-exports
anything; this experiment produces the "knee curve" showing where higher
sharpness stops being worth the memory. Expected: the knee already
measured in iTowns - between 4 and 16, see
[../AssistingRuns/docs/01_pipeline_overview.md](../AssistingRuns/docs/01_pipeline_overview.md)
- reproduces in Unreal: 8 and 4 buy sharpness at multiples of the memory,
while 32 and above return the same image as 16 at whole-area range and
give up shape up close.

### E4 - Leaf tile size: streaming granularity

Unlike E2 and E6, this experiment cannot reuse the pre-made payloads:
leaf tile size is baked into the `.bin` byte layout by `tiled_exporter`
at write time and recorded in the `.idx.json`, which `from-payload` then
only reads - so every `--tile-m` value needs its own run from the store.

```powershell
python -m voxelizer.tileset_cli from-store TestOutputs\Run7\area_output\area.npz --out-dir Run_t50  --crs EPSG:3946 --tile-m 50
python -m voxelizer.tileset_cli from-store TestOutputs\Run7\area_output\area.npz --out-dir Run_t100 --crs EPSG:3946 --tile-m 100
python -m voxelizer.tileset_cli from-store TestOutputs\Run7\area_output\area.npz --out-dir Run_t200 --crs EPSG:3946 --tile-m 200
```

Compare the three against each other, with `Run_t100` (the default leaf
size) as the baseline: number of files, tileset.json size,
time-to-first-picture on the whole-area view, and hitching while flying
at street level (`stat unit` spikes as tiles arrive). Why: leaf size
trades request overhead against fetch weight; 100 m was chosen by feel
and this experiment either confirms it or moves it. Expected: 50 m wins
on close-range streaming smoothness, 200 m on initial load simplicity;
100 m likely stays the all-round choice.

### E5 - Pyramid vs flat, safely: why the pyramid is not optional

On a small region only (500 x 500 m), export both layouts:

```powershell
python -m voxelizer.tileset_cli from-store TestOutputs\Run7\area_output\area.npz --out-dir Run_sub_pyr  --crs EPSG:3946 --region 1835000 5171000 1835500 5171500
python -m voxelizer.tileset_cli from-store TestOutputs\Run7\area_output\area.npz --out-dir Run_sub_flat --crs EPSG:3946 --region 1835000 5171000 1835500 5171500 --flat
```

Measure load behaviour and memory for both; then (optional, browser only)
point the Cesium viewer at a flat export of the full area and watch the
documented failure modes appear. Why: this reproduces, at safe scale, the
engine limits that shaped the exporter (pick-ID cap, whole-area fetch),
turning the troubleshooting war stories into a demonstrable experiment.
Expected: identical visuals on the small region; the flat full-area
control fails exactly as documented.

### E6 - Hybrid detail budget: fine where it matters

```powershell
python -m voxelizer.tileset_cli from-store TestOutputs\Run7\area_output\area.npz --out-dir Run_veg_fine --crs EPSG:3946 --keep-classes 3,4,5,8
python -m voxelizer.tileset_cli from-payload TestOutputs\Run1\area_output\area_stream.idx.json TestOutputs\Run1\area_output\area_stream.bin --out-dir Run_ctx_coarse --crs EPSG:3946
```

Two actors in one level: fine vegetation (0.25/0.1) over a coarse 1.0 m
context (ground, buildings, everything else). Toggle layers; capture the
canopy-over-context composite. Measure combined GPU cost vs the full fine
tileset from E1. Why: IA.rbre's questions are about vegetation; this is
the practical delivery shape where canopy analysis gets full detail while
the context stays nearly free. Expected: the composite costs a fraction
of full 0.25 m while looking equivalent for canopy-focused work.

### E7 - Maximum-detail close-up: inspection tileset

```powershell
python -m voxelizer.tileset_cli from-store TestOutputs\Run8\area_output\area.npz --out-dir Run_park_raw --crs EPSG:3946 --region <park bbox, ~200 x 200 m>
```

Raw store (gaps preserved), tiny region, physics allowed ON here. Use for
vertical-structure flythroughs (canopy floating above trunk space is
directly visible) and sight-line traces. Why: this is the microscope
configuration; it complements E2 by showing what the raw gaps mean
physically at the scale where they are visible. Expected: crown/trunk
separation and facade returns clearly readable; tiny tileset, instant
loads, safe physics.

## Part 3 - Measurement recipes and conventions

- **Fixed viewpoints.** Define once in `tools/example_screenshot.py`
  (whole area, district, street, facade close-up) and reuse across all
  experiments; comparability comes from identical framing.
- **Unreal metrics.** `stat fps`, `stat unit` (frame time breakdown),
  `stat gpu`, `memreport -full` (editor RSS); the Cesium panel and actor
  details expose tiles selected and geometry MB.
- **Serving.** One port per tileset (`python serve_run.py <dir> --port N`);
  keep terminals open; the browser viewer on the same port is the quick
  sanity check before Unreal.
- **Naming.** Export directories as `Run_<what>` (`Run_res_5`,
  `Run_veg_fine`, `Run_sub_flat`), so a directory listing reads as the
  experiment log. Record each export's source store and flags in a
  one-line README inside the directory.
- **Safety recap.** Physics off by default; MSSE 16 by default, 48 only
  under memory pressure; camera above the model when a tileset first
  loads; check the tileset's Georeference property points at your
  georeference actor.
