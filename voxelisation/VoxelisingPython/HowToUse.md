# How to Use the IA.rbre LiDAR Voxelizer

Turn Grand Lyon LiDAR tiles (`.laz`/`.las`) into a column-compressed voxel
grid, then get statistics, 2-D maps, per-column diagnostics, and interactive
3-D viewers - from a GUI or from the command line.

> **Install once:** `pip install -r requirements.txt`
> (`laspy` + `laszip`, with `lazrs` for the crash-isolated retry decode;
> `numpy`, `matplotlib`, `psutil`, `Pillow`, `pyproj`
> for CRS validation, `pygltflib` for 3D Tiles export. `pyvista` and
> `tkinterdnd2` are installed by that same file - nothing in it is
> conditional - but both imports are guarded, so the pipeline runs
> without either: you lose the VTK window and drag-and-drop in the GUI,
> not the run.)

> **Cross-references.** Comments and docstrings in `voxelizer/` cite the
> repository's own artifacts as the evidence behind their claims: the test
> suite in `tests/`, the measurement scripts and records in `Experiments/`,
> the eleven re-verification experiments in `code_verification/`, and the
> documents in `ReadMEs/`. The large run outputs those measurements were
> taken from are regenerated by re-running the pipeline, not tracked here.

## Quick Start (the simple section)

### The GUI - easiest way in

Double-click **`run_area.bat`** (Windows) or run:

```
python -m voxelizer.gui_area
```

The window has **two modes**:

1. **Single file** - drag & drop (or browse to) one `.laz` tile. Press Run.
2. **Area by coordinates** - type an RGF93/CC46 (EPSG:3946) bounding box
   (`xmin / ymin / xmax / ymax`), point it at a folder of tiles, press Run.
   Every intersecting tile is streamed onto one shared grid and clipped to
   your exact rectangle.

Before an area run starts, a **pre-flight dialog** shows how many tiles /
how much RAM the job is predicted to need, takes a **RAM budget in
megabytes**, and offers three buttons:
**Cancel (refuse run)**  -  **Continue anyway (RAM watchdog)**  -  **Shard beyond RAM**
(processes tile-by-tile, never holds everything in memory). Closing the
window counts as Cancel; the budget feeds both the RSS watchdog and the
sharder.

Settings are grouped into seven tabs: **Input** (file / bbox / tile folder /
download / streaming), **Voxel Grid** (cell sizes, chunking, clipping),
**Files & Outputs** (every keep/delete decision: source LAZ, voxel-grid
cache, per-stage store, pre-grouping store, column diagnostics),
**3-D Visualiser**, **Export & Serve** (3D Tiles export from a finished
store, plus serving either kind of output to a browser),
**Diagnostics** (CPU/RAM ticks + live HTML dashboard),
and **Advanced** (stage isolation, per-tile shard isolation + lazrs retry).
Hover any checkbox for a tooltip explaining exactly what it does. The
dialog couples the widgets whose combination the CLI would refuse, so a
refusal never arrives as an exit code: turning "Merge shards" off marks the
run shard-only and leaves the column diagnostics available, because those
are computed from the shards themselves. Servers started from the
Export & Serve tab are tracked separately from the job and terminated when
the window closes.

Jobs run as separate processes, so the window stays responsive and **Stop**
actually stops (shard writes are atomic, so stopping never corrupts
finished progress). After a stopped, crashed, or partial run the
**Continue...** button lights up: it can resume a sharded run's unfinished
tiles (`--resume-shards`) or re-run individual output stages from a kept
`store_raw/` (`--resume-from-store`), without re-voxelizing anything that
already completed. **Resume previous run...** does the same for any older
output folder, even from a previous session. Outputs land in
`outputs/Run<N>/...` automatically.

### The command line - three commands to know

**One tile** (stats + 4 maps + column diagnostics):

```
python -m voxelizer single path\to\tile.laz
```

**An area by coordinates** (same deliverables, one seamless grid):

```
python -m voxelizer.area_cli area --xmin 1831000 --ymin 5176500 --xmax 1832000 --ymax 5177500 --laz-dir inputs\laz
```

**Add an interactive 3-D viewer** to either - append `--viz3d`
(open the resulting `*_full.html` / `*_roi.html` in any browser), or
`--viz3d-stream` for the full-detail streaming viewer on big areas. The two
are alternatives, on `single` and on `area` alike: given both, the run renders
the streaming viewer and drops `--viz3d`.

**View a finished run** - every run that writes a viewer also writes a
double-clickable launcher beside it: `view_stream.cmd` next to a
`*_stream.html`, and `view_cesium.cmd` / `view_itowns.cmd` /
`launch_unreal.cmd` next to a `tileset.json`. The launchers contain no
absolute path, so an output folder still works after the checkout moves.
From a command line, one verb covers both kinds of output:

```
python -m voxelizer serve outputs\Run1\area_output
```

It reads the directory to decide which server to start (streaming viewer or
3D Tiles), opens a browser, and is only ambiguous if the directory holds
both, in which case pass `--kind stream` or `--kind tiles`.
`run_viewer.bat` serves the most recent streaming run directly through
`python -m voxelizer.serve_voxel_html --open`. The `scripts/` folder holds
one-purpose launchers around the same verb - drag-and-drop serving, the
Cesium and iTowns tiles pages, and Linux/macOS twins of the root
launchers - indexed in `scripts/README.md`.

That's it. Everything below is detail.

## Detailed Guide

### 1. What a run produces

Every run writes into an auto-numbered directory `outputs/Run<N>/`
(single: `outputs/Run<N>/single/<tile_stem>/`; area:
`outputs/Run<N>/area_output/`) containing:

| Artifact | What it is |
|---|---|
| `stats.txt` | Global counts, points/intervals per class, vertical extent, column heights, complexity, cross-class overlaps |
| `*_max_height.png` | Height map (see `--height-mode` below) |
| `*_max_points_class.png` | Dominant class per column (by point count) |
| `*_orthophoto_class.png` | Top-most class per column (synthetic ortho) |
| `*_n_intervals.png` | Column complexity (interval count) |
| `columns/` | Diagnostic figures + optional per-column PNGs |
| `area.npz` + `area_manifest.json` | The persisted voxel grid (area runs) - re-renderable later without touching any LAZ |
| `area_raw.npz` | The pre-grouping store (written when grouping is on; **deleted again on success** under the default `--intermediates auto` - pass `--keep-area-raw` to retain it) |
| `store_raw/` | The memory-mappable directory copy of the store that the isolated stages attach to; kept with `--keep-raw-store`, which is what `--resume-from-store` needs |
| `stages.json`, `stages/` | Per-stage execution manifest, plus `params.json` and, for every stage that ran, a `<stage>.result.json` and a `<stage>.faultlog`. The faultlog is opened before its stage starts, so a stage that succeeded leaves an empty one and only a faultlog with content records a death (area runs) |
| `shards/` | Per-tile `.npz` shards in shard mode, with `manifest.json` (lattice + grouping provenance), `run_config.json` (the parameter guard `--resume-shards` checks) and `failed_tiles.json` when a tile was lost |
| `*_full.html`, `*_roi.html` | Legacy 3-D viewers (with `--viz3d`) |
| `*_stream.html` (+ `.bin`, `.idx.json`) | Full-detail streaming 3-D viewer (with `--viz3d-stream`) |
| `view_stream.cmd` | Generated launcher written beside a streaming viewer: one double-click serves the folder on an OS-chosen free port and opens the page |

### 2. Single-tile CLI - `python -m voxelizer single`

```
python -m voxelizer single TILE.laz [-o DIR]
    [--cell-xy 0.5] [--cell-z 0.5]
    [--columns-mode diag|top|all|skip] [--columns-top-n 50]
    [--height-mode default|relative|absolute]
    [--viz3d [--max-boxes 5000000] [--roi-size 200] [--roi-cx X] [--roi-cy Y] [--no-full] [--no-roi]]
    [--viz3d-stream [--tile-m 64] [--max-instances 4000000] [--inline-threshold-mb 64]]
    [--delete-laz]
```

* `--cell-xy` / `--cell-z` - voxel size in metres (horizontal / vertical).
  Smaller = more detail, more RAM, more time.
* `--columns-mode` - per-column output: `diag` (default; 4 diagnostic
  figures), `top` (+ the N most complex columns as PNGs), `all` (every
  occupied column - slow, tens of thousands of PNGs), `skip`.
* `--height-mode` - what the height map shows: `default` auto-contrasts the
  column tops; `relative` is height above each column's own ground
  (nDSM/CHM, terrain removed); `absolute` is true altitude (DSM).
* `--viz3d` - also render the interactive Three.js viewers. The tile is
  voxelized **once**; the 3-D render reuses the same grid.
* `--delete-laz` - remove the source file after a successful run (applied
  last, so 3-D can still read it).

### 3. Area CLI - `python -m voxelizer.area_cli area`

The coordinate-driven pipeline: selects every tile whose extent intersects
your box, streams each one in chunks, clips points to the exact rectangle,
and merges everything onto **one shared grid with a single vertical datum**
(so indices and heights are comparable across tile seams).

```
python -m voxelizer.area_cli area
    --xmin X --ymin Y --xmax X --ymax Y --laz-dir DIR [-o OUT]
    [--cell-xy 0.5] [--cell-z 0.5]
    [--keep-classes 2,3,4,5,6] [--no-clip] [--no-chunks] [--chunk-size N]
    [--height-mode ...] [--columns-mode ...] [--columns-top-n N] [--columns-all-max N]
    [--group-intervals | --no-group-intervals] [--group-gap METERS]
    [--viz3d ...] [--viz3d-stream ...]
    [--download --json inventory.json [--tile-pitch 500] [--workers N] [--limit N]]
    [--stream --json inventory.json]
    [--preflight-only] [--max-rss-mb MB]
    [--shard [--resume-shards] [--isolate-tiles] [--retry-lazrs]
             [--merge-shards [--merge-band-intervals N]] [--delete-shards]]
    [--isolate-stages | --no-isolate-stages] [--stage-timeout SECONDS]
    [--keep-raw-store] [--keep-area-raw]
    [--intermediates keep|delete|auto]
    [--resume-from-store DIR] [--only-stage STAGE]...
    [--delete-laz] [--no-save-store]
```

**Getting the tiles.** Three options:
* You already have them: just point `--laz-dir` at the folder.
* Pre-download: add `--download --json <inventory.json>` - fetches every
  tile intersecting the (slightly expanded) box first, then processes.
* Fully streamed: `--stream --json <inventory.json>` - downloads each tile
  on the fly, voxelizes it, deletes it, and moves on. Best for large areas
  on limited disk.

**Filtering.** `--keep-classes 2,3,4,5,6` keeps only those ASPRS classes
(2 ground, 3/4/5 vegetation, 6 building, ...). `--no-clip` keeps whole
intersecting tiles instead of cutting at the rectangle.

**Per-column output volume.** `--columns-mode top` writes the N most complex
columns set by `--columns-top-n` (default 50). `--columns-mode all` writes
one PNG per occupied column and is capped by `--columns-all-max`: the
default cap is 500,000 columns, an explicit number sets your own, and `0`
removes the cap entirely. Above the cap the run refuses and quotes the
estimated hours and gigabytes the uncapped export would cost, so the choice
is made on numbers. Large exports fan out into `blk_XXXX_YYYY/`
subdirectories automatically.

**Crash resilience for big sharded runs.** Metropolis-scale
sharded runs can survive native decoder crashes and interruptions:
`--resume-shards` reuses every shard already on disk (validated against the
run's lattice; `shards/run_config.json` refuses mixing parameters),
`--isolate-tiles` voxelizes each tile in a child process so a crash costs
one tile (recorded in `shards/failed_tiles.json`; the run continues), and
`--retry-lazrs` grants a crashed tile one second-opinion decode with the
single-thread lazrs backend. Recommended for any run of hundreds of tiles:
`--shard --isolate-tiles --resume-shards`. The incident that produced this
layer is written up in `tests/T160/REPORT.md`.

**Interval grouping (default ON).** At fine `--cell-z`, sparse LiDAR returns
fragment one physical object (a tree canopy) into dozens of tiny intervals.
The grouping pass merges consecutive same-class intervals per column -
smaller store, fewer 3-D boxes, honest complexity diagnostics - while
preserving per-class point totals, max heights, and the ortho view exactly.
The ungrouped store is saved first as `area_raw.npz` (note: the default
`--intermediates auto` deletes it again after a fully successful run - add
`--keep-area-raw` if you want it for later re-grouping). Limit merging
across vertical gaps with `--group-gap 1.5` (metres), or disable with
`--no-group-intervals`.

### 4. Staying inside your RAM

Four escalating tools:

1. **`--preflight-only`** - print the tile count, area, predicted store size
   and peak RAM for this exact command, then exit. The estimate reads tile
   headers and the inventory only, never point data, so it costs seconds.
   Run this first on anything big.

   What it predicts from, and how well. A store costs 16 B per occupied
   column plus 13 B per interval, which is exact once the two counts are
   known, so the estimate is only as good as its guess at how many of the
   covered ground cells hold a point and how many intervals each of those
   columns carries. Both are calibrated from measurement (campaign of
   2026-08-08: ten independent 2 km x 2 km areas of Grand Lyon built at four
   grids, 40 stores, 3.55 billion points). Occupancy measures 0.951 at
   1.0 m, 0.947 at 0.5 m and 0.937 at 0.25 m, ranging 0.69 to 1.00 by area;
   intervals per column measures 2.116, 1.776 and 1.480 at the same three
   grids and does not move with `cell_z` (refining z by 2.5x at fixed
   `cell_xy` changed it from 1.480 to 1.481). Both are fitted as power laws
   in `cell_xy`, and the printed **calibrated central** figure lands within
   -4 % to +9 % of eight runs the fit never saw. The **planning** figure
   beside it is the one to size a machine by: it assumes every covered cell
   is occupied and adds the worst per-area interval tail, which puts it 1.14
   to 1.30 times above those eight measured stores and never below any of
   them.
   In local mode the LAZ headers also give a point total for free, which
   adds two constraints: an interval holds at least one point, so intervals
   can never exceed points, and a delivery denser than the calibration
   corpus (above 111 to 114 points/m2 depending on the grid, against the
   88.7 measured) gets a second, larger estimate from the point count. The
   streamed inventory JSON carries no point count, so neither applies there.
   One caveat worth knowing before you trust `Estimated peak RAM` on a
   sharded run: it models the whole merged store resident in one process,
   which is exactly what `--shard --merge-shards` avoids, so at fine grids
   it is a ceiling rather than a forecast. The measurement behind that
   statement is
   RESULTS.md of the archived campaign of 2026-08-08 (outside this delivery) (run E5_preflight_vs_rss), which
   holds the estimate and the peak RSS of six whole-metropolis runs side by
   side. Read it for the direction of the error rather than its size: those
   runs never hold the store the figure describes, four of the six peaks
   are censored by the machine's physical RAM ceiling and two of the runs
   did not finish.
2. **`--max-rss-mb 12000`** - a watchdog: if the process actually crosses
   the budget mid-run, the tile loop aborts **cleanly** and still writes
   partial outputs (stats.txt gets a PARTIAL banner) instead of grinding
   into the pagefile.
3. **`--shard`** - for jobs that should never hold one merged store: each
   tile becomes `shards/<tile>.npz`, and everything the run reports is
   computed from that shard set. Statistics and the whole of `columns/` are
   folded shard by shard by `voxelizer/shard_diagnostics.py` (a column lives
   in exactly one shard, so sums, extremes, counting histograms and top-N
   rankings compose exactly, resolved globally on the packed key), and the
   four maps are mosaicked at a bounded pixel budget. Peak memory is one
   shard plus the accumulators, whatever the size of the corpus. The 3-D ROI
   view reloads only the shards it intersects; the full view is assembled
   shard-by-shard. `--delete-shards` reclaims the cache at the end, after
   everything that reads it has run, and disables later re-rendering,
   resuming and archiving from shards.
4. **`--merge-shards`** - build the merged store when you want the artifacts
   that only exist as one store: `area.npz`, `area_raw.npz`, `store_raw/`
   and the streaming viewer. The merge is out of core
   (`voxelizer/merge_streaming.py`): `store_raw/` is assembled on disk one
   key band at a time and the stages attach to it by memory map, so peak RAM
   does not scale with the merged store. `--merge-band-intervals` is the
   RAM/speed dial, default 40,000,000 intervals per band, about 1.4 GB peak;
   halve it on a small machine, raise it to re-read the compressed shards
   fewer times. The merged phase runs under the same per-stage process
   isolation as the non-shard path, so `--no-save-store`, `--intermediates`,
   `--keep-raw-store` and `--resume-from-store` all work in shard mode too
   (`maps` is never re-run there - the bounded mosaics from the per-tile
   fold are the canonical shard-mode maps). `--only-stage` in shard mode
   selects which stages run on the merged store: `persist_npz`, `col_diag`,
   `stats`, `viz3d_roi`, `viz3d_full`, `viz3d_stream`.

A shard-only run (`--shard` without `--merge-shards`) is refused up front,
before any tile is read, if you ask it for something only the merged store
can produce: `--keep-raw-store` (`store_raw/` *is* the merge),
`--keep-area-raw`, `--only-stage` and `--stage-timeout` (the output stages
run on the merged store, and a shard-only run has none), or `--viz3d-stream`
(the streaming exporter walks one store's key order, which a set of shards
does not have). The refusal names which flag caused it. `--keep-area-raw`
in shard mode is served by a second out-of-core merge pass, so the ungrouped
store is written alongside the grouped one at the cost of a second full pass
over the shards and a second copy on disk; declining it loses nothing, since
the raw data is the shards.

### 5. Crash isolation, resume, and intermediates (area runs)

By default (`--isolate-stages`), every output stage - `stats`,
`persist_npz`, `maps`, `col_diag`, and the 3-D stages - runs in its **own
child process** attached read-only to a memory-mapped on-disk copy of the
store (`store_raw/`). A native crash (access violation deep inside
numpy/matplotlib) then costs *that stage only*: the parent survives, decodes
the death, retries once with thread-cap mitigations, records everything in
`stages.json`, and continues. Each stage gets its own faultlog under
`stages/` - empty unless that stage died - and any failure is reproducible by
hand via the exact command line logged there.

Because the child always maps the store, the four reduction stages -
`stats`, `persist_npz`, `maps` and `col_diag` - take the out-of-core path in
`voxelizer/store_streaming.py` rather than the in-RAM one. The switch is the
store, not a flag: a memory-mapped store reduces batch by batch, splitting
only on whole columns, so peak RAM is one batch plus a bounded accumulator
instead of several arrays as long as the store. The answers are identical to
the in-RAM path, quantiles included (the height median comes from an exact
counting histogram, not an approximation). `viz3d_stream` already walked the
store one tile-row band at a time; the two legacy box exports (`viz3d_roi`,
`viz3d_full`) are the exception, since their column selection still unpacks
per-column index arrays before the box cap applies.

* **`--intermediates auto`** (default): if every stage succeeded, the
  derived caches (`store_raw/`, `area_raw.npz`, `templaz/`) are deleted; if
  anything failed, everything is kept and the exact resume command is
  printed. `keep`/`delete` force either behaviour; `--keep-raw-store`
  always preserves `store_raw/`, and `--keep-area-raw` always preserves
  `area_raw.npz` (for re-grouping later with a different `--group-gap`).
* **`--resume-from-store OUT/store_raw`** - skip voxelization entirely and
  re-run the output stages from a preserved raw store. Geometry and options
  are read from its `run_params.json`; no bbox flags needed.
* **`--only-stage maps --only-stage viz3d_full`** - restrict a run (or a
   resume) to the named stage(s). The flag must be **repeated once per
   stage** (`--only-stage maps col_diag` is an argparse error). Also note:
   a stage must still be *enabled* by its own flag to run - e.g.
   `--only-stage viz3d_full` without `--viz3d` is refused with an error
   listing the stages that *are* enabled for the run (the resume path
   infers `--viz3d` from viz3d stage names automatically).
   `--only-stage _crash_test` deliberately segfaults a child so you can
   verify crash containment on your machine. Common combinations:

   ```
   --only-stage stats --only-stage persist_npz              # voxelize + save .npz only
   --only-stage maps --only-stage col_diag --only-stage stats   # re-render 2-D + stats (from cache)
   --only-stage viz3d_roi --only-stage viz3d_full --viz3d   # re-render 3-D HTML (from cache)
   ```
* **`--stage-timeout SECONDS`** - wall-clock limit per isolated stage; the
  child is killed and retried once when it expires. The default is `0`,
  meaning no limit, and that is deliberate: a fixed limit cannot tell a big
  stage from a stuck one, because the value that separates them scales
  with the store. The stage logs and faultlogs
  under `stages/` are the evidence for a hang, so this stays opt-in.
* `--no-isolate-stages` restores the historical in-process path. It has no
  stage machinery, so combining it with `--only-stage` or `--stage-timeout`
  is refused rather than silently ignored. `--shard` and
  `--resume-from-store` are exempt from the refusal: both isolate their
  stages whichever way `--isolate-stages` is set.
* **Sharded runs have their own, per-TILE resilience layer** (stage
  isolation above covers the *output* stages; `--isolate-tiles` covers the
  *decode/voxelize* loop): see the "Crash resilience for big sharded runs"
  paragraph in section 3.

### 6. 3-D viewers

Two families, both rendered from the already-built grid (the area is never
re-voxelized for 3-D):

**Legacy singleton viewers** (`--viz3d`) - self-contained HTML files using
Three.js instanced rendering; open directly from disk, fly through with
mouse + WASD:
* `*_full.html` - the whole tile/area, auto-thinned to `--max-boxes`
  (default 5 M) by striding columns.
* `*_roi.html` - a square window of `--roi-size` metres (default 200,
  centred on the occupied centre or on `--roi-cx`/`--roi-cy`), rendered at
  **full detail**.

**Streaming viewer** (`--viz3d-stream`) - for areas far beyond what a
single HTML can hold (hundreds of millions of boxes) at **full detail,
never thinned**:
* The exporter writes every interval as a 32-byte record into a spatially
  tile-contiguous `*_stream.bin` plus a `*.idx.json` index, one tile-row
  band at a time (memory-bounded regardless of payload size).
* The page treats `--max-instances` (default 4 M) as a GPU *working-set*
  budget: tiles nearest the camera (and where it is looking) are resident,
  far tiles are drawn as cheap impostor silhouettes (press **P** to
  toggle), and residency follows you as you fly.
* Small payloads (under `--inline-threshold-mb`, default 64) are embedded
  in the HTML - single portable file, works from `file://`. Larger ones
  keep the `.bin` sidecar and need an HTTP server that answers Range
  requests - which is exactly what `serve_voxel_html` provides:

```
python -m voxelizer.serve_voxel_html [DIR] [--port 8000] [--bind ADDR] [--open]
```

  With no arguments it auto-detects the most recent run folder holding a
  `*_stream.html`. `--port 0` asks the operating system for a free port, so
  several runs can be served at once, and the console prints the URL it got.
  `run_viewer.bat` wraps this with `--open`, and the `view_stream.cmd`
  written beside the page does the same with `--port 0` for that one folder.
* `--tile-m` (default 64) sets the spatial tile size: smaller tiles cull
  more finely; larger ones make fewer, bigger requests.

**Standalone 3-D CLI** - render or re-render without redoing anything:

```
python -m voxelizer.viz3d_cli single TILE.laz -o OUT [viz3d options] [--grid]
python -m voxelizer.viz3d_cli from-store OUT/area.npz -o DIR [--label name] [viz3d options]
python -m voxelizer.viz3d_cli stream OUT/area.npz --out DIR/area_stream.html
        [--region XMIN YMIN XMAX YMAX] [--keep-classes 3,4,5]
        [--max-instances 4000000] [--tile-m 64] [--inline-threshold-mb 64]
```

`from-store` loads a persisted `area.npz` - run the area once, re-render 3-D
any number of times. `--grid` also writes `.vxg` grid caches for fast
re-renders. `--delete-laz` (on the `single` subcommand) removes the source
LAZ after a successful run. `stream` also accepts `--stride` and `--max-boxes`
for compatibility with the two box exporters and ignores both with a printed
warning: cut the payload with `--region` or `--keep-classes` instead.  Python users can call
`voxelizer.show_pyvista(store)` for an
interactive VTK window, or `voxelizer.export_ply(store, path)` for a
universal mesh (CloudCompare, MeshLab, Blender).

### 7. Live run diagnostics

`voxelizer/voxel_runner_diagnos.py` is a **standalone** monitor (imports nothing from
the package - copy it anywhere) that wraps any command and records CPU, RAM
(process + system + cgroup), threads, disk I/O and process count on a
background thread, plus the exact file/line of any crash:

```
python voxelizer/voxel_runner_diagnos.py -- python -m voxelizer single tile.laz -o outputs\Run5\single
python voxelizer/voxel_runner_diagnos.py --serve -- python -m voxelizer.area_cli area ...
python voxelizer/voxel_runner_diagnos.py --view outputs\Run5\diagnosis --serve
```

(If you copy it out of the `voxelizer/` directory, adjust the path accordingly.)

Everything lands in `<run_dir>/diagnosis/` (`resources.jsonl`,
`summary.txt/json`, `run.log`, and `crash.txt` only if it crashed).
`--serve` opens a live browser dashboard; `--view` attaches one to a run in
progress. In the GUI these are the two diagnostics checkboxes.

### 8. Downloading tiles directly

```
python -m voxelizer.download_laz  --json inventory.json \

    --laz-dir inputs/laz  [--workers 4] [--limit 0] [--dry-run]
python -m voxelizer.download_orthos  ...  (same flags; --ortho-dir instead of --laz-dir)
```

(The bounds select tiles by their *origin*: a tile is downloaded when its

`--limit` caps the tile count (useful for testing).  `--dry-run` only

modes are wrappers around these tools.

The Grand Lyon 2023 inventory JSON
(`nuage-de-points-lidar-2023-de-la-metropole-de-lyon.json`) ships in the

locations are checked, in order: `inputs/quickhelpers/` beside the
`voxelizer` package, then `quickhelpers/` at the repository root. The
orthophoto inventory

### 9. Round-trip back to LAS/LAZ (reconstruct)

Reconstruct a point cloud from a `.npz` store. Pick a mode by what you need to
survive a later re-voxelization:

| mode | emits | survives |
|---|---|---|
| `density` (default) | one point per original LiDAR point (via `count`), all at the interval centre | class + counts, **not** the extent |
| `one_per_voxel` | one point per interval voxel | class + extent, **not** the counts |
| `exact` | one per voxel **+ `count - height` padding** | everything - **bit-exact** |

`exact` is bit-exact for **raw** stores only - the per-tile `shards/*.npz`.
`area.npz` is the *grouped* store, and `grouped()` merges same-class intervals
across empty z-gaps, which leaves most merged intervals with `count < height`:
`exact` refuses those outright, and a merge that does survive rebuilds the
*grouped* store rather than the original. Archive the shards and regenerate
`area.npz` from them (section 9b).

```
python -m voxelizer.reconstruct to-laz area.npz output.las
python -m voxelizer.reconstruct to-laz area.npz output.laz
python -m voxelizer.reconstruct to-laz area.npz output.las \
    --one-per-voxel \
    --z-base

# bit-exact round trip, checked
python -m voxelizer.reconstruct to-laz shard.npz shard.laz --mode exact --verify
python -m voxelizer.reconstruct to-npz shard.laz rebuilt.npz
python -m voxelizer.reconstruct verify  shard.npz shard.laz
```

`--one-per-voxel` is the legacy alias for `--mode one_per_voxel`, and
`--z-base` puts each point at its interval's base instead of its centre. The
old two-positional form (`reconstruct area.npz out.las`) still works.

Exported files carry a CRS and an `IARBRE` grid VLR (origin + cell sizes), so
`to-npz` rebuilds without any sidecar. **Rebuilding on a derived origin would
land half a cell off** - `voxelize` takes its origin from `min(x)`, which in a
reconstructed cloud is a voxel *centre*.

### 9b. Archiving a sharded run as exact LAZ

```
python -m voxelizer.archive_cli pack   outputs/Run<N>/area_output --workers 8
python -m voxelizer.archive_cli unpack outputs/Run<N>/area_output --workers 8
```

The argument is a sharded run's output directory - the one holding
`shards/` - or that `shards/` directory itself.

`pack` converts every `shards/*.npz` into `shards_laz/*.laz`, verifying each one
(rebuild + array compare) before it counts as done. Size is 0.3-1.7x the `.npz`
depending on how fine the grid is: at 0.25 m xy / 0.1 m z the `.laz` was
1.5-3.4x **smaller** on all three measured tiles, while at 1 m it is
tile-dependent (0.62-1.65x) and has to be measured.
`--replace` deletes a `.npz` only after its `.laz` verifies, and is refused
together with `--no-verify`.

**Gotchas**

- Only the **raw per-tile shards** are archivable. `area.npz` is the *grouped*
  store; grouping merges intervals across empty z-gaps and is not reliably
  invertible, so `pack` refuses anything that is not `shards/`. Regenerate
  `area.npz` from the restored shards instead - the grouping settings are now
  recorded in `shards/manifest.json` for exactly that.
- An exact-LAZ re-voxelizes **coarser** (1 m, 2 m) faithfully, but never
  **finer**: every point sits at a voxel centre, so 0.5 m -> 0.25 m yields a
  sparse lattice holding 44.5 % of the true occupied voxels. Going finer needs
  the original IGN tiles.

Rationale and measurements: `laz_roundtrip_design.md` (in `ReadMEs/`).

### 9c. Post-processing a store (denoise, absorb, resolve, group)

The semantic post-processors are store-to-store: they read one `.npz` (or a
raw `store_raw/` directory, attached by memory map) and write a new `.npz`
atomically. Every store-driven output downstream - the 3D Tiles export, the
viewers, the maps - reads the result, so this is where a cleaned or
disambiguated grid comes from.

```
python -m voxelizer.postprocess_cli INPUT OUTPUT.npz
    [--min-points [N]] [--morph [MIN_NEIGH]] [--morph-classes A,B,C]
    [--absorb] [--absorb-min-neighbour 0.75] [--absorb-max-noise 2]
    [--resolve] [--tie-margin 1] [--tie-rel 0.0]
        [--no-prefer-taller] [--no-demote-uncertain] [--class-priority A,B,C]
    [--group] [--group-gap M]
    [--stats] [--dry-run]
```

The passes always run in the order min-points, morph, absorb, resolve,
group, whatever order the flags are typed in. A pass that is not named does
not run at all, and each of `--min-points` and `--morph` takes an optional
value: bare `--min-points` means 4 and bare `--morph` means 2, the library
defaults.

What each pass does. `--min-points N` drops intervals of N points or fewer.
`--morph` drops an interval with fewer than `MIN_NEIGH` same-class
neighbours among the 8 columns around it, restricted to `--morph-classes`
when given. `--absorb` reclassifies vegetation runs sandwiched by building
inside a building-dominant neighbourhood to building, where dominance is the
building fraction among the *penetrated* 8-neighbours
(`--absorb-min-neighbour`, default 0.75) and runs of `--absorb-max-noise`
voxels or shorter (default 2) are absorbed unconditionally. `--resolve`
collapses cross-class overlaps so every voxel carries one class: counts
within `--tie-margin` of the best count (default 1) count as tied,
`--tie-rel` adds a relative band, near-ties break towards the taller
originating run unless `--no-prefer-taller`, unclassified / noise / artefact
classes lose near-ties unless `--no-demote-uncertain`, and
`--class-priority` replaces the whole preference with an explicit order.
`--group` merges vertically-consecutive same-class intervals, with
`--group-gap M` limiting the merge to gaps of at most M metres (converted as
`round(M / cell_z)`, the same arithmetic `area_cli` uses).

`--dry-run` runs the passes and reports what they would change without
writing, and `--stats` prints the full per-class point table for every pass
rather than only the classes whose totals moved. Use both together to decide
on parameters before committing a store.

### 10. 3D Tiles export

Convert an `area.npz` to 3D Tiles (`tileset.json` + per-tile `.glb`
files using `EXT_mesh_gpu_instancing`):

```
python -m voxelizer.tileset_cli from-store outputs/Run1/area.npz \
    --out-dir outputs/Run1/tiles \
    [--tile-m 100] [--flat] [--no-geoid] [--vertical-crs EPSG:5720] \
    [--height-offset 49.7] [--keep-classes 2,3,4,5,6] \
    [--region XMIN YMIN XMAX YMAX] [--crs EPSG:3946]
```

Only `--out-dir` is required. `--tile-m` is the spatial tile size in metres,
`--flat` writes the flat layout instead of the LOD pyramid, `--no-geoid` skips
the automatic geoid lift, `--vertical-crs` is the datum of the input altitudes,
`--height-offset` is an explicit lift in metres in place of the grid,
`--keep-classes` filters to fewer classes, `--region` exports a metric sub-box
and `--crs` is the horizontal CRS.

**LOD and georeferencing, both on by default.** The exporter builds a quadtree
**LOD pyramid**: interior nodes hold 2x-coarsened boxes with a halving
`geometricError` and `REPLACE` refinement, full-detail leaves at the bottom, so
a viewer streams a coarse overview first and refines as you zoom in. `--flat`
restores the legacy root -> leaves layout (every tile at full detail, no
overview). The tileset is also georeferenced: `root.transform` is a real ECEF
matrix built from the store origin, so Cesium places the model on the globe
instead of at the earth's centre. Input altitudes are read as NGF-IGN69
orthometric heights (`--vertical-crs EPSG:5720`) and lifted to ellipsoidal with
the IGN RAF geoid grid through `pyproj` - about +49.7 m near Lyon, with the grid
fetched from the PROJ CDN on first use and a warning (not a silent
mis-placement) if it cannot be resolved. `--no-geoid` treats the altitudes as
already ellipsoidal, which leaves the model roughly 50 m low against real
terrain; `--height-offset M` adds a fixed number of metres instead of
consulting the grid (`--height-offset 49.7` reproduces the Lyon lift offline).
All four flags exist on `from-payload` as well. For the mechanics see
`ReadMEs/Voxelizer-Documentation.md` section 13.

`--tile-m` defaults to `100` (metres). NOTE: `--tile-m 0` does NOT mean
"whole area in one tile" - observed behaviour is one tile per occupied
column (hundreds of tiny `.glb` files). For a single tile, pass a value at
least as large as the area extent; smaller values produce more, finer tiles.

Every level of the pyramid is written **streaming**: leaves are walked in
Morton (Z-)order, which keeps every quadtree node's descendants contiguous
at every level, so each interior node is written and freed the moment its
last child arrives. Peak memory follows tree depth rather than area, so
`--tile-m 50` or `--tile-m 25` costs the same peak as the default `100`,
and the finer leaves let 3D Tiles clients cull finely enough to hold
street-level detail within their per-instance limits.

If the conversion crashes (e.g. out of memory / too many records):
- `--keep-classes` - drop unneeded classes first
- `--region XMIN YMIN XMAX YMAX` - export only a spatial sub-area

If you already have `.idx.json` + `.bin` from a prior streaming run:

```
python -m voxelizer.tileset_cli from-payload area_stream.idx.json \
    [area_stream.bin] --out-dir outputs/Run1/tiles \
    [--flat] [--no-geoid] [--vertical-crs EPSG:5720] \
    [--height-offset 49.7] [--crs EPSG:3946]
```

The five optional flags mean exactly what they mean on `from-store` above.

**Viewing the result.** The export writes three launchers beside
`tileset.json`: `view_cesium.cmd`, `view_itowns.cmd` and
`launch_unreal.cmd`. Double-clicking one of the first two starts
`voxelizer.serve_tiles` on that directory and opens the matching bundled
viewer page; the console window it opens is the server's lifetime, so
closing it stops the server. The same thing from a command line:

```
python -m voxelizer.serve_tiles DIR [--port 0] [--bind ADDR] [--open-viewer cesium|itowns]
python -m voxelizer serve DIR --open-viewer itowns
```

`serve_tiles` sends the glTF content types and the CORS and no-cache headers
browsers need, defaults to an OS-chosen free port (printing the URL it got),
and needs no Cesium ion account. `launch_unreal.cmd` starts no server: it
hands `tilesexport/UEViz/IarbreVoxels/IarbreVoxels.uproject` to the editor
and exits. The Unreal path is documented in `tilesexport/UEViz/PIPELINE.md` at
the repository root, beside the package directory, which covers importing a
tileset through Cesium for Unreal; `tilesexport/` also carries a standalone
`AssistingRuns/serve_run.py` and its own README.

That list is the whole of `voxelizer.__all__`, 67 names. The last five bind
MODULES, not callables. `serve_voxel_html` used to be bound to that module's
`main()`, which shadowed the module itself and made every
`python -m voxelizer.serve_voxel_html` open with a runpy warning; the entry

The decoder's three non-class states describe what the beam did, and only
one of them is measured. `MEASURED_AIR` (-1) means a beam traversed the
voxel, which is a positive observation of empty space. `OPAQUE_INTERIOR`
(-2) means no beam entered it, under a roof or inside a building.
`SUBSURFACE` (-3) means the voxel lies below the ground surface, and it is
INFERRED from the ground index, never measured: airborne LiDAR returns
nothing from below ground, so there is no data there to classify. Anything
counted or rendered from `SUBSURFACE` is a consequence of the ground model,
not of a return.

Quickstart:

```python
from voxelizer import voxelize_laz, ColumnStore

store = voxelize_laz("tile.laz", cell_xy=0.5, cell_z=0.25)
print(store.stats()["n_columns"])

col = store.columns[(120, 348)]          # zero-copy view of one column
for iv in col.iter_intervals():
    print(iv.class_name, iv.height_voxels, iv.point_count)

store.save("grid.npz")                    # portable
store2 = ColumnStore.load("grid.npz")

from voxelizer.area import process_area
area = process_area((xmin, ymin, xmax, ymax), "inputs/laz", cell_xy=0.5, cell_z=0.5)
```

`store_from_laz(path)` is the inverse of `store_to_laz` - it reads the grid back
out of the `IARBRE` VLR, so an `exact` export rebuilds the source store with no
extra arguments. `pack_shards` and `unpack_shards` are `archive_cli`'s `pack`
and `unpack` under their exported names: `pack_shards(run_dir, workers=1,
verify=True, replace=False)` writes `shards_laz/*.laz` from `shards/*.npz` and
returns the archive manifest it also writes to
`shards_laz/archive_manifest.json`; `unpack_shards(run_dir, out=None,
workers=1)` restores the `.npz` shards (plus `shards/manifest.json`) and returns
its own summary. Both default to a single worker, as the CLI does; the
`--workers 8` of section 9b is `workers=8` here. Same raw-shards-only rule as the CLI in section 9b.

Key `ColumnStore` methods: `stats()`, `column_summaries()`,
`interval_counts()`, `key_bounds()`, `index_to_xyz()`, `grouped()`,
`merge()`, `save()/load()` (portable `.npz`) and `save_dir()/load_dir(mmap=True)`
(memory-mappable raw directory, used by the stage-isolation machinery).
A store can also persist its derived 2-D views as memory-mapped sidecars:
`surface_model.write_views(store, path)` / `surface_model.load_views(path)`.

### 11b. Ray queries, shade and direct sun hours

This layer is **library-only** - there is no CLI subcommand for it yet. It is
driven from Python, or from the scripts under `Experiments/`.

| Module | What it gives you |
|---|---|
| `ray_trace.py` | Full 3-D Amanatides-Woo DDA. `ColumnGridDDA(store).trace(origin, direction)` returns the first solid voxel. The reference implementation. |
| `ray_columns.py` | `CeilingDDA` - identical answers, with an exact early-out for upward rays. Use this for shade work; the recorded benchmark measures escape rays 12,547x to 114,207x faster (four to five orders of magnitude, growing as cells get finer) and the shadow-casting ground-hit rays up to ~225x faster, 1x at 1 m cells where the reference already stopped on the first solid voxel (`Experiments/ray_benchmark.json`; single-machine timings). |
| `transmittance.py` | Class-aware transmittance in [0, 1] by Beer-Lambert, instead of a boolean hit. A canopy passes some light; a roof passes none. |
| `solar.py` | Solar position (NOAA/Meeus) and the sun direction in PROJECTED grid axes, including the grid-convergence correction. |
| `sun_hours.py` | Direct sun hours per column. |

```python
from datetime import datetime, timezone
from voxelizer.data_structures import ColumnStore
from voxelizer.sun_hours import compute_sun_hours
from voxelizer.transmittance import Extinction

store = ColumnStore.load('outputs/Run1/area_output/area.npz')
res = compute_sun_hours(
    store, lat_deg=45.7647, lon_deg=4.8386,
    date_utc=datetime(2026, 6, 21, tzinfo=timezone.utc),
    ext=Extinction.provisional_canopy(0.225),
    label='class-aware', step_minutes=15)
print(res.summary())
```

The `0.225` above is the earlier return-count fit for class 5 at 1.0 m cells,
kept here because a lot of recorded output was produced with it. For a new
figure use the per-pulse value, `0.2076` at 1.0 m and `0.3256` at 0.5 m.

**Run it twice.** Once with `Extinction.opaque_only()` and once with finite
vegetation coefficients: the DIFFERENCE between the two maps is what the
volumetric material model contributes, and is the quantity worth reporting.
Either map on its own is not the result.

Three things to get right:

- **Match the coefficient to the resolution.** Extinction is derived from canopy
  thickness measured in voxels, so the fitted `k` is resolution-dependent
  (class 5: 0.3256 at 0.5 m cells, 0.2076 at 1.0 m). Use the value fitted at the
  same cell size as the store you are querying. Those two are the per-pulse
  medians in
  `extinction_fit_pulse_{0p5,1p0}.json` of the archived campaign of 2026-08-08 (outside this delivery) (run E10_per_pulse_refit_scopeA),
  and they superseded the earlier return-count fit, whose class-5 medians are
  0.3382 at 0.5 m (`Experiments/extinction_fit.json`) and 0.225 at 1.0 m (the
  `k_return_fit` block of the same E10 files). The return-count values are an upper
  bound on `k`, because a multi-return pulse is counted several times and
  deflates the transmittance it is fitted from, so anything still quoting them
  reads high.
- **This is direct beam only.** No diffuse sky, no reflection, no atmospheric
  attenuation, no cloud. It answers "how long is this point in unobstructed
  view of the solar disc, weighted by what survives the canopy" - a geometric
  question, not an irradiance figure.
- **Isolate metropolis-scale passes.** Work in blocks and write each block's
  result as you go, so a native fault costs one block and the run resumes -
  the same discipline `--isolate-tiles` applies to LiDAR decoding.

Reproduce the reported numbers (these scripts live in `Experiments/`):

```powershell
python Experiments/derive_extinction.py   # fit k from the corpus
python Experiments/run_sun_hours.py       # opaque vs class-aware
```

**Re-verify the documentation itself.** The factual claims in the code's
comments and in these documents are pinned by a standalone verification
suite (`code_verification/`): eleven
experiments that re-prove the documented claims against the real LAZ corpus
and the production stores, each printing pass/fail per claim and writing its
measurements to `code_verification/out/`. Run them all with:

```powershell
python code_verification/run_all.py
```

See `code_verification/README.md` for what each experiment covers.

### 11c. Environment variables

| Variable | Effect |
|---|---|
| `VOXELIZER_BIND` | Bind default for both HTTP servers. The desktop default is loopback; a container image sets `0.0.0.0` so published ports work. An explicit `--bind` always wins. |
| `VOXELIZER_NO_BROWSER` | `1` suppresses every automatic browser open (what the generated launchers and the tests use). |
| `VOXELIZER_LAZ_BACKEND` | LAZ decoder for this process: `laszip` (the pinned default) or `lazrs` (single-thread; reached through the `--retry-lazrs` isolated retry). `lazrs_parallel` is refused because it corrupts memory on large IGN tiles. |
| `VOXELIZER_RUN_ORDER` | Run-forming cell sort: `class_first` (the default, runs maximal per class) or `height_first` (the compatibility order that produced every pre-switch store). Per-voxel content is identical under both; leave unset unless you are reproducing older output. |

### 12. Tips & gotchas

* **Start with `--preflight-only`** for any area larger than a few tiles.
* Defaults are `cell_xy=0.5`, `cell_z=0.5` everywhere (CLI, GUI and
  library). Fine grids (0.25 m) on multi-km areas need `--shard` or a
  machine with a lot of RAM.
* `--viz3d --max-boxes` far above ~5 M produces HTML files browsers
  struggle to open; use `--viz3d-stream` instead for large scenes.
* The streaming viewer's `.bin` over ~64 MB needs `serve_voxel_html`
  (plain `python -m http.server` cannot answer Range requests).
* If an area run reports a failed stage, nothing is lost: every other
  output was written, and the console printed the exact
  `--resume-from-store` command to redo just the failed part.
* A run's **exit code is meaningful**: 0 on success, 1 when a stage
  failed, a tile was lost, or the RAM watchdog aborted with a PARTIAL
  result - so CI wrappers can branch on it directly.
* **Use Python 3.13 (or newer), not 3.11.** The project's venv and Docker
  image are on 3.13 because Python 3.11.9 on Windows was found to corrupt
  the interpreter heap under numpy-heavy work: roughly a quarter of
  processes running a plain `np.fromiter` loop would fail with impossible
  errors (a tuple decaying to an `int`, a list of ints reported as
  "inhomogeneous", access violations during garbage collection). It is
  allocator-layout dependent - `PYTHONMALLOC=debug` hides it - and it
  reproduces with no project code involved. Python 3.13 and 3.14 are
  clean on identical hardware with the same numpy build.
* For architecture details, see `Diagrams/pipeline_dataflow_diagram.md`
  (8 Mermaid diagrams).
